## 2. S4 的 P1 发现：`knownCount` 会漂移 —— **成立，是真的**

### 机制（S4 的判断，Lead 逐条核实）

```
set():  if (knownCount !== null) knownCount += 1;   ← 覆盖写也 +1
get():  unlink 过期文件时不减 knownCount
evict(): if (knownCount <= cap) return;            ← 漂移后永远 > cap ⇒ 每次都全扫
```

**Lead 实证**：目录满（200 文件）后重复覆盖写同一 key 50 次 → 平均 **0.995ms / max 2.888ms**；
原始设计（无计数器）同条件是 **0.066–0.979ms**。**S4 的 P1 成立。**

### 修法：**放弃计数器，改为摊销扫描**

```js
let sinceSweep = 16;

function evict() {
  sinceSweep += 1;
  if (sinceSweep < 16) return;
  sinceSweep = 0;
  const entries = listEntries();
  for (let i = 0; i < entries.length - cap; i++) {
    try { unlinkSync(entries[i].file); } catch { /* raced */ }
  }
}
```

**为什么不能修计数器而是废掉它**：精确计数在 `set()`（覆盖写不该 +1）和 `get()`（过期删除该 −1）两处都要维护，
任一漏掉就会漂移；**漂移后是「永远走慢路径」而不是「偶尔走慢路径」**，这是 fail-slow 的最坏形态。
摊销扫描无状态，不存在漂移。

### 实测（3 个场景，优化前 = 带 knownCount 的版本）

| 场景 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 空目录新写 | 0.066 ms | **0.062 ms** | 持平 |
| 满目录（200）新写 | 0.979 ms | **0.099 ms** | **9.9×** |
| 满目录（200）覆盖写 | 0.672 ms | **0.112 ms** | **6×**（3 轮 0.098/0.101/0.104） |

**关键**：真实场景（cap=200、TTL 900s）的稳态就是满目录 ⇒ **这一改动的实际收益是 ~9×**。
`SWEEP_EVERY=16` 是实测折中（8 时空目录涨到 0.115，16 时空目录持平 0.062）。

`cache.js` **170 行**（原 162，+8）。提交 `5ace6ba`。
