# 155 — config-declared custom MCP backend (2.15.0)

Baseline 2.14.0 (`bf8cee5`, 299 tests). Final **305/305**.

## Decision

There is no official DSH "HTTP endpoint + JSONPath" search-provider config;
official providers are JS plugins on `ctx.web.registerSearchProvider`. A
general HTTP/JSONPath adapter would expose SSRF, credential egress and schema
drift as product behavior. This version therefore adds a deliberately narrow
**custom MCP** backend, config-only:

```yaml
customBackends:
  - id: team-search
    label: Team Search
    endpoint: https://mcp.example.com/mcp
    tool: search
    authRef: TEAM_SEARCH_KEY
    enabled: true
    queryArg: query
    limitArg: max_results
    resultsPath: results
    urlField: url
    titleField: title
    snippetField: snippet
    dateField: date
    timeoutMs: 15000
    stateless: false
```

## Security constraints

- HTTPS only; DNS hostname required (no IP literal, IPv4-mapped, loopback,
  private, link-local or metadata host); no userinfo/fragment; redirects fail.
- One named MCP tool; fixed query/limit argument names; no arbitrary headers,
  expressions, HTML scraping or per-request URL.
- Credential only via `authRef` from the credentials service or environment;
  emitted as `Authorization: Bearer`, never in cache/health/logs.
- Per-call deadline capped at 60s; provider's backend budget still applies.
- Result JSON only; `resultsPath` is a dotted key path limited to 8 segments;
  `url` must be http(s); title/snippet bounded; invalid entries dropped.
- Invalid declarations are rejected with an error list and never replace a
  built-in backend. Max 8 declarations.

## Integration

- `resolveOptions` merges `custom:<id>` backends, enabled ids and
  `backendCacheKeyFields`; cache keys include endpoint/tool/mapping/authRef.
- Health reports custom ids (telemetry keyed by `custom:<id>`), and provider
  `ready()`/breaker work through the normal backend path.
- The Settings card now has an advanced JSON editor for `customBackends`
  (staged like other fields, saved as an array). It is not a per-entry form;
  `enabled` remains the activation switch and `enabledBackends` stays for
  built-in ids.

## Verification

- Validation tests: HTTP, private/loopback and duplicate rejection.
- Result mapping: structuredContent/dotted paths, URL scheme filtering.
- Backend call: named tool, Bearer header, argument mapping, extracted source.
- resolveOptions: enabled id, backend object, cache-key fields.
- Settings editor: JSON array stages/saves as an array; invalid JSON is a
  field validation error and issues no write.
- No live custom server is configured on this host; the MCP call path is
  covered by a mocked HTTP envelope and existing `mcpCall` tests.
