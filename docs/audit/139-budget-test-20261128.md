# 139 — 2026-11-28 zero-variant budget and test reliability (2.13.8)

Baseline 2.13.7 (`75f779a`, 240 tests). This is the 2.13.8 record; the
current suite is 241 tests (2.13.10 added the `shouldStartVariant` predicate
test). The 2.13.8 run was **240/240**, 15 consecutive full-suite runs green.

- **Bug: a spent deadline before the first variant returned an empty success.**
  `searchDeadline` is set before the variant loop; under a small
  `backendTimeoutMs` (or heavy host load), the first iteration could break on
  `remaining < minVariantBudgetMs` before any backend ran. `perVariant` and
  `allTelemetry` stayed empty, and the empty-success branch returned
  `{sources:[]}` instead of an error. The loop now records a zero-result
  history entry and throws `search budget exhausted before any backend could
  run` when `variantsRun === 0`.
- **Flaky tests made deterministic.** Timing tests raced the suite's parallel
  load: a 100 ms sync-throw timeout and a 600 ms starvation test. The sync
  test now has 5 s; starvation advances a stubbed `Date.now` by 1 s inside the
  first backend call instead of sleeping. The `shouldStartVariant` predicate
  test was added in 2.13.10 (audit 141), after this record.
- Tests: 15× full-suite stress, 240/240 each.

Residual: the zero-variant guard is a last-resort defence. With variant 1
starting at 50 ms, only a clock jump past the deadline reaches it; it has no
dedicated test (a `Date.now` jump probe can fire it deterministically).
