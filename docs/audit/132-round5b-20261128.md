# 132 — 2026-11-28 round-5b: plan timeout and telemetry latency (2.13.1)

Baseline 2.13.0 (`b577d6c`, 227 tests). Logic and bug reviews found four P2s in
the new fallback and multi-query budget; final **229/229** tests.

- **Do not retry a timed-out plan backend.** The plan fallback now checks
  `failure.err.timedOut`; only fast failures (HTTP 5xx, auth, connection
  refused) fall back to per-facet calls. A hung Parallel call previously
  doubled wall-clock time by retrying under a smaller later share, with no
  coverage gain. Timeout errors are tagged where the provider wraps them.
- **Telemetry latency follows the winning attempt.** The folded model-facing
  line used `max(ms)` across attempts, so a 120 ms failed plan attempt made the
  successful 6 ms result look like `p ✓124ms`, contradicting `/health` `ms:6`.
  A success now wins and keeps its own latency; failures fold to max only when
  no attempt succeeded. `skipped` is cleared by a later success.
- **Multi-query keeps the configured timeout (P2).** The per-variant share
  divided `backendTimeoutMs` by the variant count, so a healthy 1s backend
  failed at 666ms under three variants. A variant now gets the configured
  timeout while the absolute search deadline still bounds the total; later
  variants consume only what is left.
- **Exa category removed (P2).** The `tools/list` probe records
  `web_search_exa {query, numResults, objective}` only; `inferExaCategory`
  injected an undeclared `category` under `deepCoverage`. The argument and its
  README claim are gone; current docs now match the published schema.
- **Tests:** timeout plan called once; fast-fail fallback still retried;
  multi-query slow backend returns; existing plan/cache/budget tests green.

Residual: the planned Parallel call contributes sources only to the primary
variant list (RRF weight 2), not three weight-1 positions; documented, not
changed.
