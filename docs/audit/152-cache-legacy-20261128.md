# 152 — cache-key single source and legacy best-effort (2.13.19)

Baseline 2.13.18 (`9b510fc`, 281 tests). Final **285/285**.

## cache key

`resolveOptions()` now returns `cacheKeyFields` (global result-affecting
values, including `concurrency`) and `backendCacheKeyFields` (per-backend
baseURL/baseURLs/model/searchDepth/safeSearch/domains/apiKeyEnv).
`provider.js` flattens those objects instead of scanning `opts` with a regex
plus a hand-written per-backend list; `CACHE_SEMANTICS_VERSION` is 3.

`concurrency` is deliberately keyed: the shared search deadline means a
different concurrency can start a different set of backends (4 fake backends
at 400ms with a 1s budget returned 4 sources at concurrency 6 vs 2 at 1).
The drift test checks global and backend classification, values, and that
provider flattening misses for model/searchDepth/safeSearch/apiKeyEnv/baseURLs
and concurrency changes.

## legacy save

A legacy `settingsScope` without `setMany` cannot be atomic. It now reports
`partialApplied` after a mid-batch failure, reloads the host snapshot, keeps
staged drafts, and shows `legacyBatchHint` before a multi-field save and
`savePartial` after a partial failure. Validation remains all-or-nothing;
only the runtime write path is best-effort. Retrying is idempotent (same-value
writes do not advance the settings revision).

## Residual

- `breaker*` and `cacheTtlS` remain outside the key by design/old behavior.
- The client test harness still uses a lightweight hook stub; real React
  re-render behavior is review-verified, not browser-tested.
